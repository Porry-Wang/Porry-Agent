# 决策记录

只追加，不修改历史条目；新决策加在文末。

每条记录背景、决定、理由与被否方案。代码现状以代码与测试为准，架构原则见 docs/spec/00-spec-checklist.md。

## 2026-11-12 配置项按事实 / 常量 / 用户选择分类，config 收敛到 7 个字段

背景：初版 config 有 19 个字段，把压缩阈值、运行上限等全部暴露为环境变量。

决定：模型窗口、单价这类事实数据移入按模型名查询的注册表；规范确定的策略值写成代码常量；只有随用户、机器、任务变化的值（接哪个模型、密钥、日志级别等）保留为环境变量。

理由：每个环境变量都是一条额外的输入路径，配置面越大，行为偏离预期的入口越多。事实数据放全局配置还有正确性问题：主 Agent 与子 Agent 使用不同模型时，单一的全局窗口和单价必然算错。

被否方案：全量旋钮化。机制可以实现，但参数不需要全部开放配置。

## 2026-11-16 模型注册表为纯数据表，新增模型走 TOML 配置

背景：需要支持跨厂商模型（如 deepseek 与 qwen），且新增模型不应要求修改代码。

决定：模型信息集中在注册表：DEFAULT_MODELS 是内置快照，MODELS_FILE 指向的 TOML 按模型名覆盖。resolve_model 拒绝未注册的模型。

理由：注册表提供上下文窗口等事实，压缩与请求参数都依赖它；未知模型没有窗口数据，放行会让后续计算失去依据。TOML 覆盖使新增厂商只需改配置文件，形态参考 Continue 的用户配置。

被否方案：在代码中逐个硬编码新模型；LiteLLM 式未知模型直通（缺少窗口事实，有真实需求时再评估）。

## 2026-11-16 provider 表示协议而非厂商

背景：跨厂商切模需求提出时，曾考虑把 provider 字段改成厂商枚举。

决定：provider 只表示协议（mock / openai 兼容）。厂商差异由模型名、base_url、密钥环境变量名表达，挂在注册表的模型条目上。

理由：DeepSeek、Qwen、OpenAI 的请求格式相同，差异只在端点与鉴权。按协议建模，一个适配器覆盖所有兼容厂商；按厂商建模，每接一家都要新增代码分支。

被否方案：厂商枚举。密钥明文写入配置同样被否：api_key_env 只存变量名，运行时从环境变量读取。

## 2026-11-16 保留标准定为「是否直接服务主链路」

背景：models.py 初版有 18 个字段和连接解析函数，但当时没有任何代码消费它们。

决定：以「是否直接服务主链路（选模型 → 连模型 → 跑循环）」决定去留。字段作为扩展点可以保留，没有消费方的逻辑删除。ModelSpec 收敛到 5 个字段，resolve_connection 删除。

理由：没有消费方的逻辑无法被真实验证，维护成本却立即产生；等消费方出现时重建，设计依据更充分。

被否方案：一次性预支所有将来可能用到的字段与逻辑。

## 2026-11-16 主循环先于状态层实现

背景：原计划先建任务状态层，再搭主循环。

决定：先实现最小主循环；状态层等循环运行暴露出真实需求后再建，设计参考 GoalKeep 模块。

理由：状态层的职责（任务树、持久化、恢复）取决于循环实际如何消费状态；循环不存在时，这些设计只能靠推测。

被否方案：状态层先行。

## 2026-11-16 Message 承担最小上下文，独立为 messages.py

背景：完整的上下文系统（裁剪、压缩、投影）尚未建设，循环需要消息载体。

决定：Message 只含 role / content / tool_calls / tool_call_id；messages 列表保存全量历史，不做裁剪。消息结构从 provider.py 拆出，独立成模块。

理由：当前对话长度远小于模型窗口，裁剪没有触发条件。消息是循环、工具、provider 共用的数据，不应隶属于其中任何一方。

被否方案：先建压缩系统再跑循环；压缩在窗口溢出真实出现时建设。

## 2026-11-16 MockProvider 定位为产品默认离线模式，测试分三层

背景：真实 API 接入前需要验证循环与工具的完整链路；真实请求有成本且输出不确定，不适合做回归测试。

决定：MockProvider 作为产品默认的离线模式保留。测试分三层：脚本化假模型验证机制（工具执行、磁盘改动、消息配对走真代码）；httpx.MockTransport 假造 HTTP 层验证协议解析；真实 API 验证模型行为质量。

理由：三层各自隔离一个变量——决策、协议、模型行为，测试失败时能直接定位到层。

被否方案：只靠 mock 不接真实 API（无法验证模型理解与决策质量）；「未接真实 LLM 就无法测试闭环」的判断（机制正确性可以离线验证）。

## 2026-11-17 工具层首批只实现 read_file 与 edit_file

背景：模型需要操作文件，文件编辑是 CodingAgent 的核心副作用。

决定：编辑约束：先读后写；old_string 唯一匹配，多处匹配时报出候选行号；写入用临时文件加 os.replace 原子替换；写后重读校验，不一致则回滚。路径经 resolve 后校验在工作目录内，拦截 .. 与符号链接逃逸。

理由：这些约束针对真实故障：模型基于过时的文件内容编辑、匹配到错误位置、写入中断留下不完整文件。边界校验防误操作，但进程权限未被隔离，因此明确声明不是安全沙箱。

被否方案：首批加入 shell / search / write_file；等真实任务需要时再加。

## 2026-11-17 循环首版只实现两种终态

背景：基线定义了多种终态与硬上限，首版需要确定实现范围。

决定：只实现 completed（模型不再返回 tool_calls）与 max_turns 两种终态。工具异常转换为 observation 消息回传模型，不向主循环抛出异常。

理由：终止依据是模型行为而不是文本内容，避免模型口头声称完成但任务实际未完成。错误终态、墙钟与成本上限依赖尚未存在的错误分类和计量模块，届时补充。

被否方案：首版实现全部终态与上限。

## 2026-11-18 连接解析重建在 openai_provider.py

背景：provider 阶段需要把注册表中的连接字段解析为实际请求参数。

决定：resolve_connection 返回 (base_url, api_key)，按模型条目覆盖、全局配置兜底的优先级取值，错误抛 ProviderError。重试次数、超时、退避间隔为代码常量。

理由：解析逻辑放在唯一消费方旁边，注册表保持纯数据。这些参数不随用户或任务变化，不构成配置项。

被否方案：放回 models.py（注册表掺入运行时逻辑）；重试参数开放为环境变量。

## 2026-11-18 错误分类：瞬时错误重试，永久错误立即失败

背景：真实请求会遇到超时、限流、鉴权失败等错误，需要区分处理。

决定：网络错误、429、5xx 视为瞬时错误，指数退避重试最多 2 次；其余 4xx 视为永久错误，立即失败；响应结构不符合预期时报错且不重试。

理由：瞬时错误重试有意义；鉴权或参数错误重试只会重复失败；格式错误来自适配层或端点不兼容，重试无法改变结果。

被否方案：统一重试所有错误。Retry-After 响应头与熔断机制在实际遇到限流问题后再引入。

## 2026-11-18 文档策略：决策记录只追加，现状描述不进文档

背景：设计讨论发生在对话中，长期维护需要可追溯的设计依据；此前一份模块盘点文档因与基线重复、内容随代码失效而被删除。

决定：本文件只记录决策、理由与被否方案，只追加不修改。代码现状由代码、docstring 与测试承载；复杂模块落地时按需补充机制文档。

理由：决策是历史事实，写下后不会失效；现状描述需要与代码同步维护，不同步就会误导读者。

被否方案：每个代码文件配一份描述文档。

## 2026-11-18 截断回复不重试，报错并提示调大输出上限

背景：评审适配器时发现未检查 finish_reason。模型回复被 max_tokens 截断时，半截内容会当作正常回复进入循环。

决定：_parse_reply 检查 finish_reason，为 length 时抛 ProviderError，说明回复被 max_tokens 截断、应调大该模型的 max_output_tokens，不重试。

理由：截断由请求参数决定，参数不变时重试必然再次截断，只会重复花钱；截断的 tool_calls 参数可能不完整，放行会让工具执行拿到残缺输入。报错把问题交给配置侧解决。

被否方案：截断回复照常返回；对截断自动重试。

## 2026-11-18 适配器兼容厂商的实际协议偏差

背景：评审识别出三类真实端点可能偏离 OpenAI 规范的行为：http 到 https 的跳转、tool_calls 的 arguments 返回 dict 而非字符串、错误详情放在响应 JSON 的 error.message 字段。

决定：httpx.Client 开启 follow_redirects；arguments 为 dict 时用 json.dumps 归一为字符串再构造 ToolCall；错误详情优先提取 error.message，取不到退回响应正文截断 200 字符，瞬时与永久两个失败分支共用。

理由：3xx 若不跟随会落进「其余 4xx 立即失败」之外的未定义分支；dict 型 arguments 直接构造 ToolCall 会触发校验错误，被笼统包装成「响应格式不对」，掩盖真实原因；厂商错误正文常是 HTML 或空串，error.message 才是可读的诊断信息。

被否方案：严格按规范实现、遇到偏差再修（偏差可预见，修复成本低）；为 tool_call_id 为 None 加防御（循环的配对不变量已保证，不加）。

## 2026-11-18 OpenAIProvider 支持显式关闭与 with 用法

背景：httpx.Client 持有连接池，长跑调用方复用 provider 时若不关闭会泄漏连接。

决定：OpenAIProvider 增加 close() 与 __enter__/__exit__。CLI 入口在 finally 中经 getattr 取 close 关闭，MockProvider 无此方法则跳过。

理由：一次性 CLI 进程退出时操作系统会回收资源，但 provider 是公开接口，无法假设调用方都是一次性进程；上下文管理器是 httpx 自身的惯用形态。MockProvider 不持有资源，不为接口对称补空方法。

被否方案：依赖进程退出回收；给 MockProvider 补空 close 换取形式统一。

## 2026-11-18 第一个暴露界面为一次性 CLI 任务模式

背景：项目至此只有后台核心，唯一调用方是测试，需要确定真人如何输入任务；用户提出尚无前台交互模块。

决定：以 `python -m porry_agent "任务"` 的一次性 CLI 作为第一个入口，核心保持纯后台库。交互式对话推迟到状态层阶段，HTTP 服务与 Web 界面等有真实需求再建。

理由：run_loop 只认字符串输入、结果输出，暴露方式不影响核心。一次性 CLI 足以兑现 DoD 的真实任务与文件改动验证；交互式对话依赖多轮会话状态与当前模型管理，属于状态层职责；HTTP 与 Web 是产品化包装，届时只是新增调用方，核心无需改动。

被否方案：先建交互式 REPL 或 HTTP 服务再跑冒烟。

## 2026-11-18 真实 API 阶段不新增环境变量，其余上限与能力继续推迟

背景：真实 API 阶段清单需要划定范围，避免把后续阶段的能力提前堆入。

决定：不新增任何环境变量。流式输出、整轮墙钟上限、成本上限、日志脱敏、async 化推迟；usage 解析留到成本阶段，context_window 联动留到压缩阶段（届时 400 错误需细分上下文超长与参数错误）。

理由：单请求超时已覆盖请求挂死风险，整轮墙钟与成本上限依赖尚不存在的计量模块；流式输出当前无消费方，CLI 打印完整回复即可；日志脱敏等真实密钥进入日志链路时再做。延续「机制必要不等于现在实现」的保留标准。

被否方案：接入真实 API 时一并实现流式与全部运行上限。

## 2026-11-18 docstring 只补公开接口，私有 helper 不补

背景：审查全部模块的 docstring，发现覆盖不对称：部分公开函数缺 docstring，新增私有 helper 也没有。

决定：为 complete、run_loop、resolve_model、setup_logging 补一行契约式 docstring；_to_wire、_tool_to_wire、_error_detail、_parse_reply 不补。

理由：docstring 的读者是调用方，公开接口的重试行为与异常契约不应靠读实现获知；私有 helper 只有一个调用方且同文件可见，函数名已表达职责，复述名字的 docstring 是噪音。_parse_reply 的两条防御规则在代码中是显式分支，可读性足够。

被否方案：全量补齐所有函数；给 _parse_reply 单独补一句（可选项，未采纳）。

## 2026-11-18 真实 API 阶段按批次分开提交

背景：适配器与 CLI 入口分两批交付，需要确定提交粒度。

决定：两批各自独立提交，不合并为一条。

理由：两批各有独立验收点——适配器以离线测试全绿验收，入口以真实模型改动文件验收。一条提交对应一个验收点，出问题时能定位到适配层还是接线层；Review 时 diff 也更小。

被否方案：两批合并为一条提交（粒度粗，回溯定位能力弱）。

## 2026-11-18 模型窗口与输出上限改为可选字段

背景：两个数字字段原本必填，但唯一消费方（压缩模块）尚未建设；开源用户添加中转模型时，被迫在首跑前查询窗口数字。

决定：context_window 与 max_output_tokens 改为可选，缺省 None 表示未知，填了必须为正。max_output_tokens 为 None 时请求不带 max_tokens 键，使用端点默认输出上限。

理由：没有消费方的强制事实，等于把查数字的成本转嫁给每个用户；端点自身有默认输出上限，不带该参数是合法行为，截断时已有 finish_reason=length 报错兜底。

被否方案：保持必填（消费方未建却向所有用户收成本）；缺省时填保守默认值（伪造事实比承认未知更糟，压缩模块将来需要的是真实数字）。

## 2026-11-18 内置模型表收录标准：官方核实且主链路兼容

背景：内置的 deepseek-chat 已被官方停用，开箱即错；核对四家官方源时发现部分现行模型与我们的请求方式存在协议差异。

决定：内置表更新为 mock、gpt-4o-mini、deepseek-flash、qwen3.8-flash。收录标准两条：数字与端点经官方源核实；chat completions + tools + max_tokens 主链路与该模型兼容。kimi-k3 与 gpt-5.x 暂不收录：前者官方参数名为 max_completion_tokens，对 max_tokens 的兼容性未验证；后者（gpt-5.6）的 chat completions 与函数工具不能同时使用，除非 reasoning_effort=none。

理由：内置表是开箱即用的承诺，收录主链路未验证的模型等于假承诺。这些模型可经 MODELS_FILE 自行添加，参数名适配等真实接入需求出现再做。

被否方案：先收录再修（用户首跑即撞错）；只核数字不核协议（数字正确不等于能跑通）。

## 2026-11-18 两处高频配置报错说人话

背景：真实冒烟踩过两类启动失败：密钥写进 ~/.zshrc 但执行终端未 source；NO_PROXY 含非法条目 [::1] 导致 httpx 构造期抛 InvalidURL。原报错都不指向根因。

决定：api_key_env 分支的缺密钥报错追加 source 提示；构造 httpx.Client 时捕获 InvalidURL，转为点名 NO_PROXY 并给出清空前缀的 ProviderError。

理由：两类错误在开源用户中复发率高（shell 配置与代理环境因机器而异），报错里多一句话的成本远低于用户自行排查。兜底分支的 PORRY_AGENT_API_KEY 可经 .env 提供，不涉及 shell source，不加提示。

被否方案：把排查步骤写进 README 代替改报错（用户先看到报错，不是先看到文档）；请求期再捕获 URL 异常（构造期拦截已覆盖已知根因）。

## 2026-11-18 内置快照留在代码，涨到十几条再挪数据文件

背景：讨论模型事实硬编码在代码中是否合适。主流形态有代码内字典、随包数据文件（LiteLLM、Aider）、构建期抓取嵌入（Goose）、活的外部注册表（opencode 使用的 models.dev）。

决定：4 条快照暂留 DEFAULT_MODELS。触发点：开源后内置表涨到十几条，或频繁收到加模型的 PR。届时把快照挪成随包 TOML 数据文件（与 MODELS_FILE 同一 schema），load_models 先读内置文件再读用户文件。活注册表是更后面的可选项。

理由：硬编码事实的代价是腐烂与更新需发版，但 4 条规模下代价趋近于零；挪数据文件让数据更新与代码分离，社区可直接提 PR 改数据。活注册表解决几百个模型的事实保鲜，代价是网络依赖与上游滞后，当前事实的消费方都未建成。

被否方案：立即挪数据文件（无规模压力，徒增打包复杂度）；立即接 models.dev（纯预支）。

## 2026-11-18 不引入 LiteLLM SDK，Provider 缝保留可逆性

背景：讨论是否直接引用 LiteLLM 的统一接口代替自写适配器。

决定：不引入。将来需要时写一个 LiteLLMProvider 接入 build_provider 工厂，循环与工具层不动。触发点：同时需要多个非 OpenAI 原生协议，或跨厂商 fallback 成为真实需求；成本阶段需要几百个模型的单价时，优先只消费它的 JSON 数据文件而非 SDK。

理由：目标厂商全部走 OpenAI 兼容，适配层没有缺口；引 SDK 带来依赖树与版本 churn，错误被裹进它自己的异常体系（刚做的人话报错被埋掉），ModelResponse 到 Message 的转换照样要写。Provider Protocol 使该决策可逆，可逆的决策不必提前拍板。适配层也是本项目从零吃透机制的目标之一。

被否方案：现在引入 SDK（此刻没有它要解决的问题，成本却全要付）。

## 2026-11-19 配置解析链收敛进 provider 工厂

## 2026-11-20 流式输出：on_text 回调缝，首字前才重试，REPL 收尾去重

背景：REPL 等整段回复生成完才显示，长任务用户面对空白屏幕；流式的消费方随 REPL（#14）出现，交互阶段第二批开工。

决定：分三层。streaming.py 纯逻辑：parse_sse_data 逐行解析（空行/注释/[DONE] 返回 None），StreamAssembler 累积 content 碎片并返回新增文本，tool_calls 按 index 静默拼装，finish_reason 只记录不抛错。openai_provider.stream_complete 发同一请求带 stream:true，新文本实时交 on_text，拼完返回完整 Message；首个文本碎片吐出前的连接错误按既有退避重试，吐出后断流直接抛 ProviderError 不重试；非 200/截断/坏 JSON 与非流式同一套分类，截断文案共用常量。run_loop 加可选 on_text：非空且 provider 有 stream_complete 走流式，否则走 complete（MockProvider 自动回落）；一次性模式不传回调，stdout 契约不变。REPL 回调逐字打印（end=""、flush=True），streamed 标记决定收尾：流过只补换行不重打全文，半截失败也先补换行再报错。

理由：回调缝让 Provider Protocol 不动，Mock 与既有测试替身零改动；两条路径返回值都是 Message，历史结构一致，循环的工具执行与判停逻辑零改动。重试边界划在「用户是否已看到文本」：吐出后重试会重复打印半截话，宁可本轮失败（REPL 单轮失败不结束会话已兜底）。截断抛错放 provider 层，避免 streaming 反向 import ProviderError 成环；坏 JSON 透传 JSONDecodeError 由 provider 统一包装，纯逻辑层不自造异常。

被否方案：Provider Protocol 加流式方法（Mock 与全部测试替身被迫跟进）；yield 事件流（调用方自行拼装，缝变复杂）；断流后也重试（重复输出）；一次性模式同样流式（无消费方价值，退出码+stdout 契约优先）；REPL 结尾重打全文（与逐字打印重复）。

## 2026-11-20 流式缝显式化：stream_complete 进 Protocol（反转同日流式 ADR 的 getattr 探测条款）

背景：流式 ADR 决定 Provider Protocol 不动、run_loop 用 getattr 探测 stream_complete 回落 complete。实际代价随即显现：调用点无法被搜索（getattr 里的方法名是字符串），「支持不支持」从接口期降级到运行期，静态阅读失效。

决定：Provider Protocol 同时声明 complete 与 stream_complete；MockProvider 与 RecordingProvider 给退化实现（调 complete，整段当一个碎片交 on_text）；run_loop 删 getattr，on_text 非空即直调 provider.stream_complete。「回落」概念删除。

被否方案：保留 getattr 探测（调用点不可见，本轮反转的对象）；独立 StreamProvider Protocol + isinstance runtime_checkable（仍是运行期判断，且替身被迫类型化）；共享 FakeProvider 基类（核磁盘后仅 RecordingProvider 一处需要，建基类是过度抽象）。

被否方案：继续维护手写协议层（学习价值已兑现，跟踪厂商偏差的维护成本持续存在）；保留 streaming.py 作备用解析路径（无消费方，同一职责两份表示）；引 LiteLLM 替代 openai SDK（11-18 的否决理由仍成立：依赖树 churn、错误被裹进其异常体系）。

## 2026-11-23 流式完整性判据放宽：迭代正常结束即完成（修订 finish_reason 完整性守卫条款）

背景：首次真实压测（#5）即失败。线级证据：openlux 中转全程 finish_reason=null，流以 [DONE] 收尾，工具请求同样；「未见 finish_reason → 抛错」守卫把正常完成的流误判为中断。守卫来自探针假设（规范厂商发 finish_reason），真实中转违反了它。

决定：删除 finish_reason 缺失抛错分支，迭代器正常结束即视为完成；finish_reason=length 截断检查保留（有信号就拦）。对应用例替换为真实中转形状回归用例（finish_reason 全 null + [DONE] 收尾 → 正常返回）。

理由：SDK 迭代器只在两种情况结束——收到 [DONE]，或 HTTP 正文正常终结；真正的提前断连（chunked 正文未收完）httpx2 抛 RemoteProtocolError，走 APIConnectionError 中断路径，既有守卫接住。「干净早停且无 [DONE]」需线级插桩才能分辨，无真实失败案例支撑该成本。披露代价：对不发 finish_reason 的中转，length 截断检测失效；当前请求不带 max_tokens，截断风险低，真撞上按失败清单处理。中转另发 reasoning_content 思考碎片，适配器只输出 content 天然忽略，无需改动。

被否方案：维持严格守卫（误判真实中转，首压测即阻断）；线级插桩区分 [DONE]（无真实失败案例，纯预支）；厂商档案加「是否发 finish_reason」标志（协议偏差数据化可行，当前只有一例偏差样本，等第二例再抽象）。

## 2026-11-25 工具层扩展为目录列举、文件查找与内容搜索，系统提示只保留通用能力契约

决定：list_directory 只列直属目录项并支持分页；find_files 按文件名 Glob 递归查找；search_content 按 UTF-8 文本内容检索并返回路径、行号和命中行。三者统一处理分页、结果上限、依赖目录排除与符号链接越界。系统提示不再针对具体压测场景写路径猜测或禁用文件，只保留工具清单、通用能力契约和工具结果的数据边界；edit_file 的描述明确写入授权。

理由：目录、文件名和文件内容是不同的查询事实，分给不同工具后模型不必为了盘点读取全部文件。路径与遍历约束放在工具实现中，比依赖提示词遵守更稳定，也能随新工具复用。通用能力契约面向后续能力扩展，任务专用提示会随每个压测场景增长，并容易与用户指令冲突。搜索与列举结果必须有上限，否则工具能力越强，单次 Observation 越容易失控。

## 2026-11-25 强度压测按场景隔离，人工故障注入不进入真实任务基线

背景：一次 14 轮压测把 46 个真实重构文件与人工生成的 8MB huge_context.py 放在同一工作区和同一历史链中。大文件在末轮触发请求超限，同时其存在和禁用约束贯穿前序历史，干扰了多文件任务与历史总结的真实表现。多轮产物还曾散放在 smoke_ws 根目录，难以区分归属。

## 2026-11-26 read_file 分页与单次输出上限，search_content 按文件分组

背景：read_file 原先整文件返回，读取一个大文件就会把大量字节一次性灌入上下文；search_content 的命中按平铺列表返回，同一文件多处命中时路径反复出现，既浪费 token 也不利于定位。

决定：read_file 按行分页，默认 100 行、最大 500 行，char_offset 支持超长行内续读，单次输出硬上限 32000 字符；未读完时返回 next_offset 与 next_char_offset 续读坐标。search_content 同页结果按文件分组，路径只出现一次，命中行带行号缩进展示。

理由：上下文成本由单次 Observation 的字节数决定，分页把读多少变成模型可以逐步决策的动作，而不是被动接受整文件；硬上限保证超长行也不会突破单次输出预算，续读坐标让截断后的内容仍然可达。分组消除重复路径的 token 开销，同文件命中相邻呈现，模型据此可以直接定位编辑位置，减少二次读取。

被否方案：靠系统提示要求模型少读（没有执行层强制，约束不稳定）；截断输出但不给续读坐标（剩余内容不可达，模型只能猜测）；搜索结果保持平铺原始输出（路径重复计费且难以阅读）。

## 2026-11-26 run_tests 只做 pytest 进程级受限，明确不是安全沙箱

背景：Agent 需要运行测试验证改动，但开放任意 shell 会把不可控命令面引入工具层；同时测试代码本身可以执行任意 Python，这一边界必须如实声明而不是假装能防住。

决定：新增 run_tests，只运行固定 pytest 命令，无 shell、不接受自定义参数；path 必须是工作区内目录或 test_*.py、*_test.py 文件；环境变量走白名单，不继承 PYTHONPATH、pytest 插件自动加载与厂商密钥；60 秒超时、64KiB 输出上限，超时终止整个进程组；测试失败作为正常结果返回退出码，超时与输出超限才是工具错误。描述明确不是安全沙箱，且只能在用户明确要求运行测试时调用。

理由：固定命令加环境白名单把注入面收敛到参数校验一层，比过滤危险命令稳定得多；进程组终止避免超时后孙进程继续占用资源；测试失败是模型修复问题所需的信息，作为正常结果返回才能让模型看到失败详情继续工作。进程级受限防不住测试代码内部的恶意行为，所以边界写进工具描述，由写入授权契约约束调用时机。

被否方案：通用 shell 执行工具（命令面不可控）；建设 seccomp 或容器级真沙箱（平台绑定重，当前阶段属于提前建设）；把测试失败当工具错误（模型丢失修复所需的失败信息）。

## 2026-11-26 apply_patch 扩展增删移，整批预检后顺序写入

背景：apply_patch 首批只支持更新既有文件，真实重构需要新增、删除和重命名，且这些操作经常出现在同一批改动中，拆成多次调用会留下跨工具调用的中间态。

决定：补丁格式支持 *** Add File、*** Delete File，以及 Update File 区段内的 *** Move to（允许无 hunk 的纯移动）；Add 内容行仅以 + 开头，Delete 无内容。整批先预检路径合法性、目标不存在、源文件先读、路径别名与目标冲突，全部通过后顺序写入，活动失败走内存回滚。

理由：增删移放进同一补丁，模型一次调用就能表达完整重构意图，跨文件一致性由工具保证而不是依赖模型自觉；整批预检把可发现的失败挪到任何写入之前，多数错误不产生副作用；移动挂在 Update 区段的目标路径上，复用同一套 hunk 匹配逻辑，内容修改与重命名在一处完成。

被否方案：增删移拆成独立工具（调用次数增加，跨文件一致性失去保证）；边写边检查（失败时已写文件需要回滚，失败面扩大）；顺带支持 End of File 等扩展语法（没有真实需求，不提前建设）。

## 2026-11-26 多文件写入采用 Journal 崩溃恢复，冲突保留外部修改

背景：apply_patch 逐文件写入，内存 try/except 回滚依赖进程活着；进程在中途被 kill 或崩溃时，工作区停在改了一半的状态，比完全没改更危险，且用户不知道哪些文件被动过。

决定：新增 journal.py：写入前把旧值备份与 manifest 状态机（prepared/applying/committed）落盘，工作区文件锁保护，文件与目录 fsync；启动或下次写入前扫描日志，prepared/applying 逆序回滚，committed 只清理。恢复时当前内容既非旧值也非新值则判定为外部修改，标记 needs_attention，保留现场并阻断后续写入。活动写入失败仍走内存回滚，Journal 的冲突保守策略只用于崩溃恢复。不承诺断电与硬件级绝对原子。

理由：回滚信息落盘后，收拾残局的是下一个活着的进程，不再依赖崩溃进程的异常路径；状态机区分未写、写入中、已完成，恢复动作由落盘事实决定而不是猜测。外部修改可能是用户手工编辑，强行覆盖会造成真实数据丢失，宁可停下等人工处理。活动失败会产生写后损坏（内容既非旧也非新），这类内容必须强制回滚，若复用冲突保留策略会把自身写坏的文件误判为外部修改，破坏既有失败语义。

被否方案：承诺断电级绝对原子（需要文件系统或硬件支持，超出工具层能力）；活动失败也走冲突保留策略（写后损坏得不到回滚）；冲突时强行回滚（覆盖用户手工编辑）。

## 2026-11-26 启动恢复接线入口，冲突降级为只读而不是拒绝启动

背景：Journal 恢复能力落地后需要触发点：遗留事务应在进程启动时处理并告知用户结果；出现冲突或日志损坏时，要决定拒绝启动还是降级运行。

决定：入口在工具构造后调用 recover_workspace，回滚与清理信息走 stdout，冲突与损坏走 stderr 警告，启动不中断；edit_file 与 apply_patch 写入前再次恢复并拦截冲突、损坏与锁占用；干净工作区不创建状态目录。.porry_agent 加入递归遍历排除名单，list_directory 仍如实显示。

理由：遗留事务不影响只读操作，拒绝启动会把用户锁在工作区外，连排查问题的读取能力都失去；降级为只读保留排查手段，写入拦截防止损害扩大。写入前复查覆盖启动之后新出现的遗留事务（例如并发进程崩溃）。排除状态目录避免日志备份污染搜索结果、浪费 token；list_directory 如实显示与 .git 的处理一致，保留人工检查现场的入口。

被否方案：冲突时拒绝启动（用户失去排查能力）；只在启动恢复、写入前不复查（启动后出现的遗留事务会被直接写入）；对 list_directory 也隐藏状态目录（与既有目录处理不一致，用户看不到现场）。

## 2026-11-26 apply_patch 新增与移动目标自动创建父目录

背景：真实压测中模型按任务新增 tests/test_price.py，被"父目录不存在"整批拒绝；新增文件伴随新目录是真实开发常态，模型只能降级把文件放到别处，任务字面要求无法达成。

决定：Add File 与 Move to 目标允许父目录缺失，预检只拒绝父路径含符号链接或存在非目录祖先；应用阶段逐层创建缺失父目录并记录在案，活动失败回滚时逆序 rmdir 清理（只删空目录，非空即保留）。预检保持无副作用。崩溃恢复只按 Journal 文件记录回滚，新建的空目录可能残留，作为已披露边界接受。

理由：预检阶段建目录会让"整批预检失败不产生副作用"的承诺失效；应用阶段创建并记录，回滚才能精确清理自己创建的目录。rmdir 只删空目录，外部进程放入的内容不会被误删，与 Journal 冲突保留的保守取向一致。符号链接祖先拒绝，防止借道符号链接把写入引向工作区其他位置。

被否方案：预检阶段创建目录（预检失败留下副作用）；把目录写进 Journal manifest（扩大事务schema，空目录残留无数据风险，收益不抵复杂度）；维持拒绝并要求模型先建目录（没有建目录工具，等于把缺口推给提示词）。

## 2026-11-26 冻结评测集与探索压测分工，通过率趋势作为 Agent 能力度量

背景：此前每轮压测题目与判分器临时设计，只能回答"这次改动有没有 bug"，无法回答"Agent 是否变强"；功能验证与能力度量混在一起，代码持续改进缺少不动的参照系。

决定：建 evals/ 冻结评测集：8 题来自已验证场景，题面、初始文件（SHA-256 锁定）、判分器固定，版本标识 2026-11-26。主指标只有终态正确性（每题 0/1，重复 3 次报通过率），有测试的题做 p2p 判定并防改松（基线断言数与关键数值不减）；过程指标单独记录不混入总分。执行器每次运行把代码 commit、题集版本、模型、每题通过率追加进 ledger.jsonl。改题面、fixture 或判分器必须升级版本；探索压测继续自由变题，发现修复后沉淀为下一版题目。

理由：度量能力变化需要固定尺子，题目随代码改动会让通过率失去可比性；模型输出随机，单次通过/失败噪声大，重复执行报通过率才能区分波动与退化；模型自述不可信，判分必须独立执行并防止删断言过测试；账本记录 commit 与题集版本，趋势才能归因到具体改动。

被否方案：每轮压测兼任评测（标准漂移，无法纵向比较）；过程指标计入总分（把模型波动误读为能力变化）；首版建 L3 自动归因与 LLM-as-Judge（确定性判分器已够用，不提前建设）；token 指标首版纳入（缺请求边界日志，估算不可信，如实不做）。

## 2026-11-26 平台口径定为全平台兼容，输出收集走单一跨平台代码路径

背景：审查发现 run_tests 用 selectors 监听子进程输出管道，而 Windows 的 DefaultSelector 只支持 socket，run_tests 在 Windows 必然失败；journal 与 test_runner 里的 msvcrt、taskkill 等 Windows 分支从未经任何测试执行。用户明确有其他设备要运行本项目，否决了收敛 POSIX 的提议，口径定为 macOS/Linux/Windows 全兼容。

决定：输出收集改为读取线程加队列的单一代码路径，三平台行为一致，删除 selectors 与 os.set_blocking 平台条件；终止与恢复路径不再用 communicate 读管道，避免与读取线程争抢同一管道。OS API 确实不同的分支保留（fcntl/msvcrt 锁、killpg/taskkill 终止、Windows 跳过目录 fsync），用 monkeypatch 平台名加桩模块的路由测试保证接线正确，真实行为由用户在 Windows 设备按验收清单闭环。权限断言平台条件化：Windows 的 os.chmod 只切换只读位，测试在 Windows 断言可写位语义而非完整权限位。

理由：双分支方案会让一半代码永远没被执行过，正是本次缺陷的成因；单一代码路径在 macOS 上就能被全部超时、截断、多块重组测试真实验证，Windows 不再有未验证的特殊路径。路由测试本机可跑，保证平台分支至少接线正确；没有 Windows CI 之前，设备验收是唯一诚实的真实验证手段。

被否方案：收敛为 POSIX 并删除 Windows 分支（用户有真实跨设备需求，被用户否决）；Windows 单独写一套输出读取分支（重蹈未验证代码覆辙）；声称支持 Windows 但不补验证手段（纸面适配，与本次缺陷同构）。

## 2026-11-28 Journal 损坏输入显式校验，状态路径与备份禁止越界

背景：审查发现 manifest 中的非对象条目、不可哈希状态或 kind、过深 JSON 会在恢复前触发运行时异常；backup_name 若被改成绝对路径、相对路径或符号链接，可能读到事务目录之外；Journal 状态目录自身若为符号链接，也会使写入逃逸工作区。原子写入还需要区分文件同步与目录同步的失败语义。

决定：读取 manifest 时校验版本、状态、entries，以及每条记录的 path、kind、backup_name、new_sha256、mode、new_mode 类型和取值，backup_name 只接受数字加 .bak。所有 Journal 入口先解析并校验状态目录，拒绝符号链接路径组件和越界结果；备份目录与备份文件必须解析到事务 backups 目录下的直属普通文件。非法输入统一转换为 journal_corrupt，由恢复报告记录并阻断写入，保留现场，不自动修复。原子写入在 POSIX 先设置临时文件权限再同步和替换，Windows 只表达可写位语义；文件 fsync 失败保留旧文件并报错，目录 fsync 失败仅告警，临时文件清理和事务目录清理不遮蔽原始异常。

理由：日志是外部可篡改或损坏的输入，必须在进入恢复逻辑前完成形状校验，不能依赖后续字典和集合操作恰好安全。路径与备份的解析结果必须落在预期边界内，符号链接和相对穿越不能因为 manifest 可写就被信任。文件内容是否持久化决定写入结果，目录元数据同步失败则只降低持久化保证，不应把已经完成的文件替换误报为失败；保留原始异常才能让调用方获得真实故障原因。

被否方案：用宽泛异常捕获掩盖所有损坏（丢失故障分类且可能继续写入）；信任 manifest 中的备份路径（允许越界读取和符号链接绕过）；把所有 fsync 失败都当作写入失败（目录同步能力差异会制造假失败）；自动删除或修复损坏日志（破坏现场证据，也可能覆盖用户外部修改）。
